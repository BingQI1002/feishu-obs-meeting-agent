# 核心：会后记录与 OBS 回流

## 先保全尾部信息

会议结束信号出现后，立即保存尚可读取的尾部事件、会议元数据和可用产物标识。飞书的会中事件存在有限的会后可见窗口；不要先清理身份再尝试补取材料。

如果用户在会议仍进行时要求停止，按用户授权停止监听并离会；只基于已经取得的材料生成记录，明确覆盖范围。

## 先完成会后深读

检查 `agent-state.md` 的 `Post-meeting deep-read queue`。非空时：

1. 在飞书发一句“会议已结束，正在继续关联你的历史材料”；
2. 保持当前 Agent 任务运行，不立即给最终答复；
3. 先读相关项目和主题页，再沿链接追溯必要原始材料；
4. 结合 `events.jsonl` 检查会议现场，不用记忆代替；
5. 把新增、修正、冲突、机会和下一步写入候选；
6. 达到本机配置的检索迭代上限仍不足时，明确材料缺口并停止，不无限扩读。

## 两层内容

### 会议事实包

只记录会议中有依据的内容：

- 会议主题、时间、参会人和原始产物入口；
- 会议实际要解决的问题；
- 关键讨论与不同观点；
- 明确决定；
- 明确行动项、负责人、时间和验收标准；
- 风险、待核实和未闭环事项；
- 与上次同类会议相比的推进、重复或倒退。

没有明确说出的负责人、日期、决定、数字或承诺必须留空或标待确认，不能让语言模型补齐。

### Agent 判断候选

单独记录 Agent 在会中形成、值得后续继续验证的内容：

- 新的解释、机会或结构性风险；
- 被现场证据挑战的旧判断；
- 用户未必采纳的建议；
- 需要更多材料才能确认的假设；
- 本次主动私信及用户后续反馈。

Agent 候选不能混入会议事实，更不能写成用户已经确认的决定。

### 会后深度分析

会后分析不是更长的摘要，至少覆盖：

- 这场会与用户过去哪些材料真正相关；
- 相比过去新增了什么；
- 哪些既有判断得到支持、修正或挑战；
- 对当前项目或下一次协作有什么影响；
- 哪些内容值得写 OBS，哪些只留飞书原始记录。

## 会后确认卡

散会并完成必要深读后，先生成 `writeback-candidate.md`，再向已授权的飞书接收人发送完整但可扫读的确认卡；当前 Agent 聊天框镜像同一份内容，供用户修改或确认。发飞书不等于写 OBS：仍然必须等用户确认后才落库。

会后卡没有固定栏目。根据本场实际内容，自然组织会议真正留下的产出、行动与未决点、Agent 新判断，以及确认后准备更新的既有 OBS 位置。用户应能直接回复“确认”、修改某一条或“先不写”。

可以使用短段落、加粗、项目符号或编号帮助扫读；没有内容的部分直接省略。会议事实与 Agent 推断要能自然区分，但不必为了分类增加生硬标签。完整逐字稿、冗长过程和后台检索细节不进入飞书卡。

在发送确认卡前，必须先把同样内容连同覆盖范围、原始产物入口、已读 OBS 证据和已发私信写入本场状态目录的 `writeback-candidate.md`。文件不存在时不得发送会后卡。飞书投递成功后，把消息 ID 与幂等键追加到状态；投递失败时不重发同一内容，而是在当前 Agent 对话说明失败原因并保留候选。

## 归位由个人 OBS 决定

通用 Skill 不规定所有 OBS 都必须建立“每场会议页＋滚动页”。先读取个人 OBS 的正式入口，再决定：

- 是否建立单场会议记录；
- 是否更新相关项目、人物页、会议系列或行动清单；
- 哪类事实可以直接写入；
- 哪类内容必须在聊天中预览确认；
- 原始逐字稿、纪要或妙记只保留链接，还是需要保存副本。

完整逐字稿、智能纪要和妙记继续留在飞书。运行态原始事件只为恢复和核对暂存在本地，不默认复制到 OBS。

用户确认后，优先把必要事实、决定、行动和未闭环更新到已有相关项目或会议系列。不要为了每场会机械创建一份新的 OBS 会议纪要。没有明确项目归属或本地没有写入规则时，保留候选并请求用户选择，不自行创建新的 OBS 架构。

## 跨会议连续性

回流完成后的检验不是“文件写好了”，而是下一次相关会议能否快速找到：

- 上次定了什么；
- 谁承诺了什么；
- 哪些事项仍未闭环；
- 哪些判断已经被新证据修正；
- 这次最需要继续观察或追问什么。

重复会议的记录应更新已有的连续性入口，而不是机械复制一份新的总表。

## 会后回执

向用户简短说明：

- 监听是否完整停止；
- 记录覆盖到哪个时间；
- 事实记录与 Agent 候选分别有哪些；
- 哪些内容已按本地规则写入，哪些仍等确认；
- 下一次相关会议可从哪里继续。

技术完成和建议价值分开报告，不以“生成了一份纪要”替代价值验证。
