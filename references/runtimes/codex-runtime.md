# 运行环境：Codex

## 目标

把监听器 stdout 中的每个会议批次真正交给当前 Codex Agent 处理。监听脚本在后台运行不等于 Agent 被唤醒；只有当前任务持续读取进程输出并进入判断循环，才算主动会议能力成立。

## 当前可执行方式

1. 用 Codex 的长运行终端能力启动监听器，并设置较短的首次 yield，取得持续会话 ID。
2. 保持当前 Codex 任务处于工作状态，不结束回合。
3. 使用会话续读能力阻塞等待新输出；单次等待控制在 30–50 秒，便于向用户保持必要的状态沟通。
4. 收到一行 `feishu_meeting_batch` 后，立即按主 Skill 的判断循环处理，而不是只打印 JSON。
5. 判断完成后回到同一终端会话继续等待，不重新启动监听器。
6. 收到 `feishu_meeting_ended`、用户停止请求或不可恢复错误后，进入尾部抓取和回流。

在当前 Codex 工具面中，这通常对应：

```text
启动长运行终端命令 → 获得 session_id
循环调用终端会话续读（如 write_stdin 空写入）→ 取得新增 stdout
处理事件并私信 → 继续续读
```

不要把普通 shell 后台进程当成唤醒机制：如果 Codex 已经结束回合，单独留在后台的 stdout 不会自动变成新的 Agent 判断。

## 启动检查

真实入会前验证一次最小回放：

- 监听器输出一个 fixture batch；
- 当前 Codex 任务在没有用户新消息的情况下读到它；
- Codex 能继续读取下一批，而不是在第一批后结束；
- 停止命令能终止监听器且会话 ID 不再产生输出。

这项检查失败时，只能报告“飞书事件抓取可用，Codex 主动唤醒未闭合”，不得继续声称已经能够主动私信。

## 状态与压缩

每个实质批次处理后更新 `agent-state.md`。Codex 上下文压缩或任务恢复后，先读取该文件和监听器状态，再续读同一会话；无法恢复原终端会话时，使用同一状态目录重启监听器并依靠事件去重续接。

## 用户中途发消息

用户的新消息优先处理，但除非用户明确停止，不改变监听状态。处理完后回到同一会话继续等待。不要因为收到普通问题就启动第二个监听器。

## 当前支持范围

这份适配器只证明 Codex 的运行方式。Claude、MOMA 和 Hermes 必须分别验证“长运行进程输出如何成为 Agent 回合”；复制主 Skill 文件本身不会自动获得主动唤醒能力。
